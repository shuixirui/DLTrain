# 开发者贡献指南

欢迎参与 MegatronAdaptor（以下简称 MA）的开发！

MA 是 Megatron-LM 在昇腾 NPU 上的非侵入式适配层：训练入口增加一行 `import megatron_adaptor` 即可完成算子适配、兼容性修复与加速特性启用，不修改 Megatron-LM 源码。因此，MA 的贡献场景以**适配点（Patch）的修复与新增**为主，而非在仓内实现模型或训练特性。

开始开发前，请先阅读 [项目简介](docs/zh/introduction.md) 与 [目录结构](docs/zh/dir_structure.md)。

## 一、贡献方式

### 1.1 问题反馈

提交 issue 前，请先检索已有 issue，避免重复。问题描述需包含：

- **环境信息**：MA 分支、Mcore 版本或 commit、TransformerEngineNPU 与 CANN / torch_npu 版本
- **现象**：完整报错栈或精度/性能异常现象
- **复现步骤**：启动脚本、并行策略、关键训练参数
- **最小复现**：能够稳定触发问题的最小模型规模与数据集配置

环境版本组合是 MA 问题定位的前提，信息不全的 issue 往往无法复现。

### 1.2 适配需求与方案提案

上游 Megatron-LM 持续演进，MA 通过夜航自动化看护（megatron-adaptor-sync）每日同步上游并回归验证。以下改动需先提 issue 讨论方案，再提交代码：

- 新增适配点（新算子替换、新兼容修复、新加速特性）
- 调整既有 Patch 的生效条件或默认行为
- 涉及多个维护版本分支的改动

提案中请说明：目标上游版本与符号、当前失效原因、适配方案、对已有特性的影响、是否需要新增训练参数。

### 1.3 文档与测试修正

文档错误、示例失效、测试用例缺失可直接提交 PR；涉及行为变更的文档修正，请与对应代码改动一并提交。

## 二、提交前必读（红线）

1. **绝不修改 Megatron-LM 源码**。一切适配通过本仓 Patch 机制完成；Megatron-LM 仓库仅作只读参考，确需向上游提 PR 时遵守上游规范。
2. **新特性禁止默认使能 Patch**（原生特性适配除外）。基础适配固定生效；其余功能必须由训练参数门控，默认关闭。
3. **统一通过本仓补丁机制注册**。禁止在仓内直接修改上游模块属性，禁止在 import 阶段执行与适配无关的重操作。
4. **多版本兼容先探测**。修改或新增 Patch 前，确认目标符号在支持的 Mcore 版本范围内可用，不可假设符号一定存在。
5. **不兼容必须拦截**。与其他特性冲突时显式报错，并在文档中写明兼容性说明。
6. **特性内聚**。特性本体与框架适配解耦，一特性一目录；禁止上帝类/函数；单函数不超过 200 行，单文件不超过 1000 行。
7. **不改 TENPU**。TransformerEngineNPU 侧问题不在本仓修复，应在上游对应仓库处理。

## 三、贡献流程

```plaintext
问题/适配需求 → issue 讨论方案 → 代码开发 → 测试验证 → 文档同步 → PR 提交 → CI 门禁 → 代码检视 → 合入
```

1. **提交 issue**：在 GitCode 提交 issue，说明问题或提案；标题建议注明类型，如 `[Bug]`、`[Adapt]`、`[Doc]`。
2. **方案确认**：涉及新增适配点或行为变更的，先在 issue 中确认方案，避免返工。
3. **开发与自测**：按第四章规范实现，补充单元测试，本地跑通后再提交。
4. **提交 PR**：按 [PR 模板](.gitcode/PULL_REQUEST_TEMPLATE.md) 填写背景、用户可见影响与测试情况，并关联对应 issue。
5. **触发门禁**：在 PR 评论 `compile` 触发 CI。门禁执行单元测试与基础训练系统测试；仅文档变更（`*.md` 与 `docs/` 下文件）时跳过用例构建。具体触发方式与检视要求以仓库当前配置为准。
6. **代码检视与合入**：通过门禁并完成代码检视后由 Committer 合入；检视意见需逐条回复或修改。

## 四、Patch 开发规范

### 4.1 开发步骤

MA 采用“特性（Feature）+ 补丁（Patch）”两层结构：`features_manager/` 负责参数注册、门控与补丁注册，`patches/` 存放具体替换实现。

新增或修改一个适配点，按以下步骤进行：

1. **定位上游符号**：确认目标模块与符号路径，并确认其在支持的 Mcore 版本中存在。
2. **探测可用性**：参考 `patches/patch_utils.py` 中的探测方式，在注册前判断模块或符号是否可用；跨版本差异较大的适配点应分别处理或显式跳过。
3. **实现替换函数**：放到 `patches/` 下对应维度目录（`requirements/`、`megatron/`、`transformer_engine/`）。
4. **注册到特性**：在 `features_manager/` 下对应维度目录（`requirements/`、`megatron/`、`megatron_fix/`、`transformer_engine/`、`functional/`）新增或扩展特性类，并登记到内置特性清单。
5. **补测试与文档**：补充单元测试，并同步更新相关文档。

### 4.2 补丁模式

按目标符号与改动意图选择补丁模式：

- **覆盖式**：目标符号已存在，用 MA 实现整体替换。
- **装饰式**：在原逻辑前后追加处理，必须保证原函数仍被执行；函数名以 `wrapper` 或 `decorator` 结尾，框架按装饰器叠加。
- **缺省创建**：目标符号在部分版本或依赖未安装时不存在，由 MA 提供兜底；仅限确有兜底意义的场景，不得掩盖真实的适配遗漏。

同一目标默认只允许一个整体替换，重复替换会报错，需要叠加逻辑时使用装饰式。需要同时修改初始化与执行逻辑时，优先新建类整体替换；不兼容特性命中同一修改点时，使用工厂模式或参数门控选择实现。

### 4.3 特性门控与上游缺陷修复

- 特性类负责注册训练参数、校验参数与注册补丁；补丁注册分两个阶段：上游模块导入前替换底层接口，导入后替换业务函数。
- 基础适配特性固定生效；功能特性默认关闭，需满足优化等级要求并打开对应开关。
- 与已有特性不兼容或存在依赖关系时，在参数校验阶段显式报错，并在文档中写明兼容性说明。
- **上游缺陷修复**：问题若为 Megatron-LM 在 GPU 上同样存在的共性问题，参考 `MegatronFixFeature` 实现，新增 `--fix-*` 开关控制，默认关闭，行为与上游修复保持一致，并在上游合入后删除该补丁。
- 同一适配点覆盖多个维护版本时，在 PR 中说明验证过的上游版本范围。

### 4.4 代码质量

| 指标 | 要求 |
|---|---|
| 单个函数行数 | ≤ 200 行 |
| 单个文件行数 | ≤ 1000 行 |
| 命名 | 清晰准确，禁止模糊表述 |
| 上帝类/函数 | 禁止 |
| 注释 | 英文注释，简洁准确，不复述代码 |

设计原则：

1. **架构解耦**：特性本体与框架适配分离，便于复用到其他框架。
2. **语义不变**：使用装饰器时保证原函数一定被执行，不改变原有语义。
3. **善用抽象**：提前考虑版本迭代，避免代码腐化。

## 五、测试与文档

- 新增或修改 Patch 必须补充单元测试，放在 `test/unit_tests/` 对应维度目录，参考已有用例。
- 用例以模块间、类间接口为观察对象，覆盖主要场景；单卡可覆盖的不要引入分布式初始化。
- 系统测试放在 `test/system_tests/feature_tests/` 并在 `test_cases.txt` 注册；ST 依赖真实多卡与固定数据集，本地不执行，交由 CI。
- 用户可见变更需同步更新 `docs/zh/` 下对应文档：适配点更新 `patch_list.md`，参数更新 `features_list.md`，已知问题更新 `FAQ.md`。
- 文档说明问题、方案、使用限制与效果；新增文件添加版权声明。

## 六、提交要求

- 提交前执行 `pre-commit run --all-files`，检查项以仓库配置为准。
- Commit message 标题使用英文，正文使用中文，简要概括改动内容与影响。
- PR 关联对应 issue，类型标签与改动一致；不要提交临时文件与日志。
- 改动影响多个维护版本时，在对应版本分支分别提交 PR。

## 七、社区准则与许可

- 保持专业、友好的沟通，聚焦技术讨论，及时响应检视意见。
- 引入第三方代码前确认开源协议兼容性，并在 PR 中说明来源。
- 所有贡献按本仓 [LICENSE](LICENSE) 条款授权。

感谢每一位开发者的贡献！
