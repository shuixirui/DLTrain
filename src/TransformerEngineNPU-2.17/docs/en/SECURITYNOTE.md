# TransformerEngineNPU Security Declaration

The security hardening measures listed in this document are basic hardening recommendations. Users should re-examine the network security hardening measures of the entire system based on their own business. Users should perform relevant configurations according to the security policies of their organization, including but not limited to software versions, system hardening requirements, security configurations (data storage, debugging interfaces, runtime environments, etc.), permission configurations, and firewall settings. When necessary, users can refer to excellent hardening solutions in the industry and the advice of security experts.

## System Security Hardening

It is recommended that users enable ASLR (Level 2), also known as **Address Space Layout Randomization**, in the system. This can be configured as follows:

```bash
echo 2 > /proc/sys/kernel/randomize_va_space
```

## Running User Recommendations

For security considerations, it is recommended that you avoid using administrator-type accounts such as root when executing any command, and follow the principle of least privilege.

## File Permission Control

- It is recommended that users set the system umask value to 0027 or higher on the host (including the host machine) and in containers, ensuring that the default maximum permission for newly created folders is 750 and the default maximum permission for newly created files is 640.
- It is recommended that users implement security measures such as permission control for sensitive files, including files required for training, files saved during training, users' personal privacy data, and commercial assets. For example, control the write permission of dataset files in multi-user shared dataset scenarios. It is recommended to refer to Table 1 for the permissions to be set.
- TENPU is installed from source code via `pip install -e`. Users need to perform proper permission control during installation and use, and it is recommended to refer to Table 1 for settings. If installation/uninstallation logs need to be saved, add the parameter `--log <FILE>` after the installation/uninstallation command, and pay attention to proper permission control for the `<FILE>` file and its directory.
- When TENPU's Triton operators (`transformer_engine/pytorch/triton/`) are executed for the first time, Triton-Ascend compiles the kernel just-in-time. TENPU does not explicitly specify a cache directory, and the cache location is determined by Triton-Ascend's own default rules (usually `~/.triton/cache`, which can be specified via the `TRITON_CACHE_DIR` environment variable). It is recommended that users refer to Table 1 to perform proper permission control for generated files and directories.
- The `torch.compile` path controlled by `NVTE_TORCH_COMPILE` in TENPU (enabled by default) caches compilation artifacts at runtime. The cache location is determined by PyTorch (usually `~/.cache/torch/inductor`, which can be specified via the `TORCHINDUCTOR_CACHE_DIR` environment variable). It is recommended that users refer to Table 1 to perform proper permission control for generated files and directories.
- TENPU itself does not read or write datasets, model weights, or checkpoint files on disk, nor does it create log files. Dataset index files, checkpoint files, TensorBoard logs, and other files generated by the caller (Megatron-LM, MegatronAdaptor, etc.) during training have permissions that depend on system settings and the caller's implementation. It is recommended that the user currently executing the script properly control permissions for generated files according to their own needs, and the permissions to be set can be configured by referring to Table 1.
- TENPU's numerical debugging capability (`transformer_engine/debug/`) relies on the third-party `nvdlfw-inspect` package to output observation logs. The on-disk path of the logs is determined by the configuration file of that package and is outside TENPU's control. It is recommended that users perform proper permission control on its output directory.
- When using TENPU for training, do not modify the permissions of files other than data assets and training scripts.

## Data Security Statement

- When loading a model checkpoint, TENPU deserializes its extended state (`_extra_state`), which involves the following two implementations:
  - The `set_extra_state` in `transformer_engine/pytorch/module/base.py` and `transformer_engine/pytorch/ops/op.py` calls `pickle.loads` in the **default format** (byte tensor) branch to restore the state. Both locations are marked with `# nosec`, and their input is data serialized by this module's own `get_extra_state`;
  - The `set_extra_state` in `transformer_engine/pytorch/module/base.py` calls `torch.load(state, map_location="npu")` in the **legacy format compatibility** (`io.BytesIO`) branch, without explicitly specifying `weights_only=True`.
- In PyTorch versions below 2.6, the default parameter of `torch.load` is `weights_only=False`, which poses a potential security risk (CVE-2025-32434). The PyTorch version bundled with this release is 2.10.0 and is not affected by this default value. When users run TENPU on other PyTorch versions, they should explicitly specify `weights_only=True` when loading checkpoints from untrusted sources.
- During the use of TENPU, model loading and saving operations may be executed. It is particularly important to note that the underlying implementation may use the Python `pickle` module for serialization/deserialization of some files, and this module has inherent security risks. Load checkpoints and weight files only from trusted sources.
- To support the normal loading of checkpoints of TENPU quantized tensors (`Float8Tensor`, `MXFP8Tensor`, `Float8BlockwiseQTensor`, etc.) under `weights_only=True`, TENPU calls `torch.serialization.add_safe_globals` when `import transformer_engine.pytorch` is executed, adding the storage types of the aforementioned quantized tensors, the corresponding Quantizer types, the `__reduce_ex__` reconstruction functions, and `signal.Signals`/`signal.SIGTERM` to the deserialization whitelist of this process (see `transformer_engine/pytorch/__init__.py`). This registration process relaxes the global whitelist scope of **all** `torch.load` calls within this process. Users should be aware of this.
- TENPU relies on the basic capabilities of CANN to implement functions such as operator dump and log recording. Users need to pay attention to the permission control of the files generated by the preceding functions.

## Runtime Security Statement

- Users are advised to write the corresponding training script based on the resource status of the running environment. If the training script does not match the resource status, for example, the memory size required for loading the dataset exceeds the memory capacity limit, or the data generated locally by the training script exceeds the available disk space, errors may be triggered and cause the process to exit unexpectedly.
- When an exception occurs during running, TENPU exits the process and prints error information. It is recommended to locate the specific error cause based on the error prompt, including methods such as setting operators to execute synchronously, viewing CANN logs, and parsing the generated Core Dump files.
- TENPU enables the `torch.compile` path by default (controlled by the environment variable `NVTE_TORCH_COMPILE`, whose default value is `1`). Additional compilation overhead is incurred when the operator fusion path is executed for the first time. If compilation-related issues are encountered or you want to avoid runtime code generation, you can set it to `0` to disable this path.
- TENPU relies on torch_npu and CANN to provide device-side execution and collective communication capabilities. In distributed scenarios, the communication itself has no authentication and is not encrypted. For its risks and hardening methods, see [Communication Security Hardening](#communication-security-hardening) and [Communication Matrix](#communication-matrix).

## Public Interface Statement

- TENPU maintains the same library name, module path, and interface signature as the native TransformerEngine (NVTE), and provides Ascend-specific extension interfaces on this basis.
- **The public interface list is subject to the interfaces recorded in the [API List](api/api_list.md).** For interfaces marked as "aligned with NVTE" in that document, their public nature in NVTE also applies to TENPU. Interfaces marked as "Ascend extension" are new public interfaces added by TENPU.
- Unlike some Ascend repositories, TENPU's `transformer_engine/__init__.py` adopts the eager re-export approach to align with NVTE release_v2.17, and **does not use `__all__` to define the export set**. Therefore, `__all__` is not used as the basis for determining public interfaces. If a function/class is recorded in the API list, then that interface is a public interface and can be relied upon as a public function. For its specific usage and applicable scenarios, refer to this document and the official NVTE documentation.
- If you need to rely on a function that is not recorded in the documentation, submit an Issue on the homepage of this repository to confirm with us whether the function is a public interface, whether it was exposed accidentally, or whether it may be removed in the future.

## Communication Security Hardening

TENPU itself does not listen on any port, does not create sockets, does not call `torch.distributed.init_process_group`, and does not proactively initiate any network communication. In distributed training scenarios, all communication capabilities are provided by the `torch.distributed` process group already initialized by the caller, as well as by torch_npu/HCCL.

Therefore, the communication security hardening requirements in this section are consistent with the existing constraints of CANN and TorchNPU. For the specific hardening methods (such as using iptables to restrict external access to communication ports before distributed training starts, cleaning up firewall rules after training ends, and the corresponding script templates), see:

[Communication Security Hardening Instructions](https://gitcode.com/Ascend/pytorch/blob/v26.1.0-pytorch2.10.0/SECURITYNOTE.md#%E9%80%9A%E4%BF%A1%E5%AE%89%E5%85%A8%E5%8A%A0%E5%9B%BA)

## Communication Matrix

TENPU is an algorithm library and does not add any listening ports itself. Its runtime network communication is carried entirely by the PyTorch distributed components and the HCCL component of CANN, and the port, authentication, and encryption characteristics are completely consistent with the caller's environment, as shown in the following table. For more detailed instructions, see [Communication Matrix](https://gitcode.com/Ascend/pytorch/blob/v26.1.0-pytorch2.10.0/SECURITYNOTE.md#%E9%80%9A%E4%BF%A1%E7%9F%A9%E9%98%B5).

### Special Scenarios

| Scenario                                  | Usage                                         | Port | Possible Risk       |
|-------------------------------------| ------------------------------------------------ | ---------- | ---------- |
| Context parallelism (Ulysses/Ring/KV-AllGather/Swap and other strategies) | Call `DotProductAttention` and specify the strategy via `cp_comm_type`; TENPU establishes a context-parallel sub-communication group via `torch.distributed.new_group` on top of the process group already initialized by the caller | Reuses the caller's process group port; no new port is added | The sub-communication group inherits the unauthenticated and unencrypted characteristics of the caller's process group; the risk is consistent with the caller's distributed environment |
| torch_npu fused communication operators | TENPU reads the HCCL communication domain name already created by the caller via `get_hccl_comm_name` and passes it as an opaque handle to the relevant fused communication operators of `torch_npu` | Reuses the caller's HCCL port; no new port is added | The communication process is controlled by torch_npu and CANN; TENPU is unaware of its port details |
| CPU Offload | Offload activations/weights to host memory layer by layer via `get_cpu_offload_context` | No network involvement | Offloaded data resides in host memory; attention must be paid to host-side memory isolation and access control |
| Numerical debugging | Configure output of online observation data via `DebugQuantizer`/`GroupedDebugQuantizer` together with `nvdlfw-inspect` | No network involvement | Debug artifacts may contain intermediate model values; file permission control must be performed as described in Table 1 |
| Test and CI scripts | Distributed test scripts in `tests/` and `ci/` use loopback addresses such as `MASTER_ADDR=localhost`; `get_free_port` in `tests/pytorch/utils.py` briefly binds port 0 on the wildcard address to obtain a free port | Loopback address or a port randomly assigned by the operating system | Used only for local single-machine testing and does not provide services externally; `get_free_port` binds port 0 and does not expose services |

## Vulnerability Response

We attach great importance to the security of the community version. The Ascend open-source community receives, investigates, and discloses security vulnerabilities related to this community. For details, see [Ascend Vulnerability Response](https://gitcode.com/Ascend/community/blob/master/docs/security.md).
